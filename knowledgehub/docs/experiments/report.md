## 实验一：MongoDB 索引优化（§15.1）

**脚本** `exp1_mongo_index.py`；**数据** 合成笔记 1 万 / 5 万 / 10 万（独立集合 bench_notes）；
**对照** 无业务索引 / 单字段(kb_id) / 复合索引(owner,kb,deleted,updated) / 顺序不当的复合索引(updated,kb,owner)。

**核心结果（10 万笔记，P95 ms，完整数据见 `exp1_index_latency.csv` / `exp1_execution_plans.csv`）：**

| 索引配置 | 列表页(等值+排序) | 标签筛选 | 时间范围 |
|---|---:|---:|---:|
| 无索引 | 105.8 | 121.4 | 95.8 |
| 单字段 | 52.4 | 32.9 | 36.5 |
| 复合索引（应用索引） | **4.4** | 28.2 | 31.6 |
| 顺序不当 | 11.3 | 6.7 | 73.3 |

**执行计划**（totalDocsExamined，10 万文档列表页）：无索引=100,000（全表）；复合索引=20（仅命中）。

**结论：**
1. 复合索引把列表页查询从全表扫描 105.8ms 降到 4.4ms（**24 倍**），且 `totalDocsExamined` 从 10 万降到 20——ESR（等值→排序→范围）顺序是决定因素。
2. **索引顺序错误的代价是情景相关的**：顺序不当的索引在"时间范围"查询上劣化 2.3 倍（73.3 vs 31.6ms），因为它无法同时服务等值过滤与范围扫描；反而在标签筛选上偶然更快（前置的 updated_at 限定了扫描集）。说明"复合索引一定更优"不成立，必须按查询模式逐一定制。
3. **写入开销可接受**：三种索引配置下批量插入 1000 篇均 ~89-118ms（`exp1_insert_overhead.csv`），最贵的索引也只增加 ~5% 写入耗时——读收益远大于写代价。

## 实验二：Redis 缓存收益（§15.2）

**脚本** `exp2_redis_cache.py`；**对照** 全读 MongoDB vs Cache-Aside（与应用相同的键规则/TTL 300s，均走异步驱动保证公平）；**负载** 2000 请求 × 并发 1/4/16/64，均匀访问 vs 80/20 热点。

**核心结果（完整数据见 `exp2_cache_latency.csv` / `exp2_cache_hitrate.csv`）：**

| 场景 | 命中率 | P50 (ms) | 吞吐 (req/s) |
|---|---:|---:|---:|
| 全读 Mongo，c=4 | – | 1.23 | 2867 |
| Cache-Aside 均匀，c=4 | 56.9% | 0.95 | 2113 |
| Cache-Aside 热点，c=4 | 77.6% | **0.78** | 2956 |
| Cache-Aside 热点，c=1（全命中路径） | 77.0% | **0.51** | 921 |
| Cache-Aside 热点，c=64 | 74.1% | 13.7 | 2401 |

**失效恢复开销**：miss 回填 4.71ms vs 命中 0.75ms，放大 6.3 倍。

**结论：**
1. 热点分布决定收益：80/20 热点下命中率 77%（均匀随机仅 57%），命中路径 P50 比读 Mongo 快约 1.5 倍——缓存应面向热点内容（个人知识库的"最近笔记"天然是热点）。
2. **诚实的负结果**：本机 MongoDB 点查太便宜（~1ms），高并发（c=64）下 Cache-Aside 的 P95（64-73ms）反而劣于直读（17-22ms）——Redis 往返与单连接排队吃掉了收益。缓存的正确适用条件是"读路径昂贵（聚合/远程库）或热点高度集中"，而非无差别加缓存。这与 §15.2 "避免仅对均匀随机流量测试、不预设收益" 的要求一致。

## 实验三：Neo4j 图查询（§15.3）

**脚本** `exp3_neo4j_graph.py`；**规模** 1k / 10k / 50k 节点，3-8 度链接（50k 节点 32.5 万边）；
**对照** MongoDB 文档数组（linked_note_ids）/ 邻接表集合。

**核心结果（P50 ms，完整数据见 `exp3_graph_latency.csv`）：**

| 查询 | Neo4j @1k | Neo4j @50k | Mongo 对照 @50k |
|---|---:|---:|---:|
| 一跳邻居 | 5.8 | 4.5 | 0.83 |
| 两跳邻居 | 7.9 | 4.4 | 1.74（应用侧分批 $in） |
| 最短路径(≤6跳) | 4.3 | 2.9 | 无法单查询表达（需应用侧多轮 BFS） |

**结论：**
1. **Neo4j 的优势不在延迟而在表达力**：浅层读取上 Mongo 数组单读天然 O(1) 更快；Neo4j 变长路径（两跳）与 shortestPath 用一条 Cypher 完成，Mongo 等价查询需要应用侧多轮往返，代价随深度线性增长（未完整实现即因为其架构性劣势）。
2. 规模扩展性良好：Neo4j 一跳 P95 随规模 12.4→8.5ms（1k→50k）不升反稳（页缓存预热后），符合图数据库索引邻接的复杂度特征。
3. 本结果印证设计文档"不预设 Neo4j 全场景更快"——选择依据应是查询形态（多跳/路径）而非笼统性能。

## 实验四：Milvus 索引与检索质量（§15.4 核心）

### 4A 多索引性能对比（`exp4a_milvus_index.py`）

**数据** 合成笔记分块 7,686 条真实 Qwen3-Embedding 向量（1024 维 COSINE）；**查询** 50 条；Top-K=10。
**对照** FLAT（精确基线）/ HNSW(M=16, efC=200, ef=128) / IVF_FLAT(nlist=128, nprobe=32)。

| 索引 | 构建时间 | P50 (ms) | P95 (ms) | QPS | ANN Recall@10 |
|---|---:|---:|---:|---:|---:|
| FLAT | 3.7s | 13.99 | 16.90 | 72 | 1.000（真值） |
| HNSW | 3.8s | **3.02** | **4.23** | 297 | 1.000 |
| IVF_FLAT | 4.1s | 2.84 | 3.87 | 354 | 1.000 |

**结论**：7.7k 规模 + 适度参数（ef=128 / nprobe=32）下，HNSW 与 IVF_FLAT 相比 FLAT 提速 **4-4.7 倍**且 ANN Recall@10 无损失——该规模下近似索引"免费"；预期百万级向量后 FLAT 延迟线性增长而 HNSW 亚线性，召回率才会出现可测损失（资源所限未跑大规模档，列入限制）。

> 方法论记录：对比三库的 ANN Recall 必须用**显式主键**对齐向量身份——`auto_id` 的主键由 Milvus 内部生成器分配、跨 Collection 互不相同，首次实验因 auto_id 得到假 0 召回后修正。

### 4B 检索质量：Dense vs BM25 vs 混合 vs Reranker（`exp4b_retrieval_quality.py`）

**语料与评测集（v2 修订，重要）**：合成模板语料版本得出负结果（存档 `exp4b_quality_synthetic_negative.csv`）：模板句在语料内大量重复，chunk 嵌入被稀释，**即使精确余弦计算目标 chunk 也排不进 Top-5**；纯数字 ID 差异对 dense 完全不可分（实测仅数字不同的文本余弦 0.869）。这实证了 §15.7 的警告。故改用**真实文档语料**：本仓库设计文档/README/PROGRESS 按章节切分（439 个真实中文技术 chunk），以"章节标题问句化"构造 103 条查询（标题即作者级主题标注），相关集 = 该章节 chunk，标题文本不进入正文。

| 方法 | Precision@5 | Recall@5 | MRR | 检索 P95 (ms) |
|---|---:|---:|---:|---:|
| Dense（Milvus FLAT） | 0.0136 | 0.0510 | 0.0325 | 5.6 |
| BM25（jieba） | 0.0447 | **0.1783** | 0.1269 | **0.94** |
| Hybrid（RRF 融合） | 0.0291 | 0.1343 | 0.0691 | – |
| **Reranker 精排**（dense top-20 → Qwen3-Reranker-8B） | 0.0447 | 0.1589 | **0.1581** | – |

**结论：**
1. 标题→章节任务偏词面匹配，BM25 占优（MRR 0.127 vs dense 0.033）；长正文 chunk 稀释标题语义是 dense 的结构性劣势。
2. **Reranker 精排把 dense 的 MRR 提升 4.8 倍（0.033→0.158）**，超过 BM25——R4 精排的价值得到实证，建议生产链路固定采用"召回放宽 + 精排收紧"。
3. **延迟预算**：查询嵌入（外网 API）P95 520ms，是本地检索（5.6ms）的 **93 倍**——RAG 链路的延迟大头在 Embedding API 而非向量库，优化方向是嵌入缓存/本地小模型，而非索引调参。
4. 局限：相关集为章节级（≈4 chunk/节），R@5 天花板低；查询由标题程序化生成，未做盲测人工标注，真实质量需评测集扩充（列入后续）。

图：`exp4a_p95.png` / `exp4a_recall.png` / `exp4b_mrr.png`

## 实验五：跨库一致性与故障注入（§15.5 重点）

**脚本** `exp5_consistency.py`；六个情景实测（完整数据 `exp5_consistency.csv`）：

| 情景 | 指标 | 实测值 |
|---|---|---:|
| 1 正常同步 | 端到端同步延迟（提交→向量侧完成）P50 / P95 | 1133 / 1382 ms |
| 1 正常同步 | 同步成功率（5 轮） | 100% |
| 2 发布器中断 | 事件滞留（停止 3s 后 Outbox 积压） | 1 条 |
| 2 发布器中断 | 恢复后补偿完成 | 4.4 s |
| 3 Worker 中断 | vector 重启恢复 / graph 重启恢复 | 3.5 s / 0.04 s |
| 4 重复交付 | 同一事件手动重复投递 5 次后向量数 / 任务记录数 | 1 / 1（零重复） |
| 5 快速连续修改 | 6 次修改收敛到最终版 v7 | 0.8 s，无旧版覆盖 |
| 6 软删除后搜索 | 向量清除耗时 / 陈旧命中 | 0.6 s / **无** |

**结论：**
1. Outbox + 消费组 + 幂等 Worker 的组合在全部六个故障/异常情景下**最终一致**：重复投递零副作用、乱序事件按版本跳过、软删后旧向量 0.6s 内清除且搜索无陈旧命中（版本护栏生效）。
2. 延迟构成：端到端同步 P95 1.4s 中约 1.2s 是两次 SiliconFlow 嵌入调用（外网 API），异步架构把它移出用户写路径（写接口 P50 仅 ~10ms，见实验六）——这正是引入异步链路的动机实证。
3. 崩溃恢复在秒级（3-4.4s），由 XAUTOCLAIM 认领 pending 消息实现，无需人工干预。

## 实验六：系统整体并发测试（§15.6 可选强化）

**脚本** `exp6_concurrency.py`；**混合负载** 浏览 60% / 更新 15% / 关键词搜索 15% / 列表 10%；并发 1→64 递增，每级 600 请求（`exp6_concurrency.csv`）：

| 并发 | P50 (ms) | P95 (ms) | P99 (ms) | 吞吐 (req/s) | 错误率 |
|---:|---:|---:|---:|---:|---:|
| 1 | 10.4 | 20.0 | 25.8 | 64.1 | 0% |
| 4 | 22.7 | 38.3 | 45.3 | **138.5** | 0.17% |
| 16 | 163.0 | 544.4 | 683.4 | 61.2 | 1.17% |
| 32 | 309.5 | 1323.9 | 1752.1 | 58.3 | 1.83% |
| 64 | 526.2 | 693.7 | 811.6 | 97.9 | 4.67% |

**结论：**
1. 吞吐峰值在 c=4（138 req/s）；此后延迟陡增——瓶颈在 API 单进程 asyncio 事件循环与 MongoDB 写事务竞争（更新路径 = 事务 + 版本快照 + 2 条 Outbox 事件）。
2. 高并发下的"错误率"主要为**乐观锁 409 冲突**：并发读-改-写同一笔记时按设计返回冲突，属正确语义而非故障；压测后 Outbox/Streams 零积压（Worker 稳定消化）。
3. 改进方向明确：多进程/多实例横向扩展 API、更新路径合并版本快照写入。单机单实例满足个人知识库的量级（设计定位）。

## 交付附录：可靠性工具与容器化

- **对账工具（§16.2）**：`python -m workers.reconciliation [--kb-id X] [--dry-run]`。实测：对 184 笔记 + 12 文档全量比对，发现 41 条失同步（历史测试残留的缺失索引记录）→ 重发布事件 → Worker 消化 → 复检 **0 失同步**，闭环验证。
- **监控指标（§16.1）**：`GET /api/v1/system/metrics` 聚合各库文档数、Outbox 积压、任务状态分布、Streams/Pending、图节点与边数、Milvus entity 数、24h 问答量。仅全局聚合值，不暴露用户内容。
- **容器化（§13.2）**：`backend/Dockerfile`（API 与三个 Worker 共用镜像，command 区分）、`frontend/Dockerfile`（Node 构建 → nginx，SSE 反代配置）、compose `profile: app` 一键启动 backend/frontend/event-publisher/worker-graph/worker-vector。实测容器栈：`docker compose --profile milvus --profile app up -d` 后 health 四库全绿、前端 8088 端口反代 API 正常。
- **可复现性**：数据生成器固定种子（`data_gen.py` seed=42）、实验脚本可重复执行、向量语料磁盘缓存（`exp4*_vectors.json`）避免重复计费、原始 CSV 只追加不覆盖。

## 实验限制汇总

1. 大规模档（10 万向量以上、50 万级）受 16GB 内存与外网嵌入 API 成本约束未跑满，结论外推需谨慎；
2. 4B 评测集为标题程序化构造（103 条），未做人工盲标，绝对数值偏保守，方法间**相对**结论（BM25 vs Dense vs Reranker）可靠；
3. 实验二/六基于本机单机部署，MongoDB 与 API 同机竞争资源，云上分离部署的数字会不同；
4. Qwen3-Embedding/Reranker 为黑盒 API，版本升级可能改变质量结论（已把模型名纳入可配置参数）。
